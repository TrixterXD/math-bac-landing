## 1. Design objective

Recreate **Design Concept A — Warm & Playful** as faithfully as practical. Preserve hierarchy, warm cream surfaces, coral primary accents, lilac secondary accents, dark navy typography, rounded cards, teacher-led hero, playful handwritten/math annotations and spacious section layout.

**Priority:** fidelity at a specified desktop viewport → visual consistency → deliberate responsive adaptation. Do not achieve screenshot similarity at the cost of semantic HTML, accessibility, working controls, or understandable CSS.

**Image ≠ verified content.** A synthetic composition may resemble Nastya but is not evidence that depicted people, teaching results, prices, testimonials, programs or videos are real. A portrait asset derived from the supplied photograph is available for prototype development; Nastya’s permission for public/commercial use and the accuracy of any accompanying claims must be confirmed before launch. Use only approved facts or clearly marked demo content, according to `PRODUCT_SPEC.md`.

## 3. Typography

- **Approved primary font: Manrope**, integrated in `src/app/layout.tsx` with `next/font/google`, Latin and Cyrillic subsets, variable weights and `display: "swap"`. Next.js downloads the font during build and self-hosts it; the browser does not request Google Fonts. Font download failures must be reported, not worked around with a different technology.
- `--font-manrope` is generated by Next.js; `--font-body` adds Arial/Helvetica/sans-serif fallbacks. Body uses `--font-size-body: 1rem` and `--line-height-body: 1.5`; `--font-size-heading: 2.5rem` is the placeholder heading size, not a final landing heading scale. Headings use `--line-height-heading: 1.15`.
- Large, heavy geometric/modern sans-serif headings; smaller, legible sans-serif body text. No handwritten font is implemented.
- Heading feel: bold (approximately 700–800), tight but legible line-height. Key phrase can be coral.
- Body: approximately 16–18 CSS px on desktop and 15–16 CSS px on mobile, with readable line-height.
- Decorative handwritten captions are **optional visual assets**, not a substitute for meaningful content, and should remain subordinate to primary headings.
- Avoid copying garbled/generated image text or inventing copy from the mockup.

## 4. Layout and rhythm

- Desktop: central max-width content region approximately 1120–1200 CSS px; comfortable horizontal gutters. **The 941px reference image is a downscaled composition and is not a literal CSS viewport measurement.**
- Section order remains: Hero → Nastya & Team → Advantages → Programs → FAQ → Contact. Header and Footer are shared in `RootLayout` (A-018).
- Hero: two-column structure, strong left-aligned message and CTA, dominant teacher portrait on the right.
- Teams/advantages: varied compositions, not repetitive identical grids everywhere.
- Programs: two visually distinct cards (coral wash and lilac wash).
- FAQ: simple accordion treatment; native semantic `details` remains a valid first option.
- Contact: friendly headline next to a short, accessible form.
- Start with a restrained spacing scale such as `4, 8, 12, 16, 24, 32, 48, 64, 80` CSS px; refine during visual comparison.
- Card radii: approximately 16–24px; button radii: rounded/pill; soft shadows, not strong floating effects.

### Implemented foundation tokens and usage

- Spacing: `--space-1`, `--space-2`, `--space-3`, `--space-4`, `--space-6`, `--space-8`, `--space-12`, `--space-16`, `--space-20` correspond to 4, 8, 12, 16, 24, 32, 48, 64, 80px at the default 16px root size (implemented in rem).
- Shape: `--radius-card: 1.5rem` and `--radius-pill: 9999px`.
- Layout: `--content-width: 75rem` (1200px at the default root size), used as a maximum width; horizontal padding belongs to each component.
- CSS Modules consume global tokens directly, e.g. `padding: var(--space-6)`, `background: var(--color-surface)`, `border-radius: var(--radius-card)`. Inherit the body font by default; no token imports or wrapper components are needed.
- Global defaults set border-box sizing (including pseudo-elements), remove body/heading/paragraph margins, inherit fonts in form controls, and constrain media to their container. Component modules own their spacing and sizing.
- Accent colors are provisional; do not assume white text on coral/lilac meets contrast requirements. Validate actual foreground/background pairs when controls are implemented. No controls or focus-style overrides are introduced in TASK-D01.

## 6. Responsive strategy (new design work, not present in source image)

Desktop and mobile Hero now have distinct approved visual references. The approved mobile concept is **Variant C**: heading and description → portrait → three compact icon benefits → CTA → demo disclaimer; hide the introductory pill on mobile. Place the math note near the heading and pyramid/lesson note beside the portrait. Do not hide required artwork merely on an untested assumption; any clipping or readability-driven exception needs evidence and developer review. Tablet/small-desktop concerns still need their own verification; do not claim pixel-perfect fidelity at unspecified viewports.

- Prefer responsive grid/flex layouts over fixed absolute coordinates for core content.
- On narrow screens: preserve the approved Hero Variant C hierarchy, portrait, benefits and accessible CTA; the CTA need not fit entirely above the fold. Stack program cards and keep form fields usable and labels accessible.
- Choose actual breakpoints only when the content requires a layout change; avoid hardcoding arbitrary media queries before testing.
- Check 360–390px mobile, ~768px tablet and an agreed desktop width (suggest 1440px) as starting review widths.
- Honor reduced-motion preference if adding motion later.

## 7. Image-to-code review workflow

1. Agree on **one small scoped task** and allowed files (next: desktop Hero TASK-005A, then mobile TASK-005B).
2. Implement semantic and responsive structure with CSS Modules, applying the token system sparingly.
3. Take a screenshot at the agreed desktop viewport; compare with the relevant component reference (Hero: `design/reference/hero/desktop.png`) and check full-page consistency against `design/reference/landing-desktop.png`.
4. Record **observable differences**: position, text wrap, spacing, color, size, assets and decoration.
5. Fix the largest fidelity gaps before micro-tuning; compare mobile separately.
6. Run Biome, typecheck, build and relevant manual interactions; developer reviews the diff before commit.
7. For components with dedicated references, inspect the component-specific
image alongside the full landing reference. Prefer the component reference
for visual details and the full image for overall composition.

No image-to-code agent should treat the artwork as source of truth for business facts, functional behavior, prices, team identities or privacy statements.
